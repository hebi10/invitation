# 일일 공용 체험 모드 설계

## 1. 배경

이 프로젝트는 관리자가 청첩장을 만들고 고객에게 소유권을 연결한 뒤, 고객이 같은 위저드와 대시보드에서 내용을 편집·관리하는 운영 흐름을 제공한다. 현재는 Firebase 관리자 또는 고객 계정이 필요하므로 면접관이 포트폴리오의 전체 제품 흐름을 직접 확인하기 어렵다.

메인 화면에서 바로 시작할 수 있는 체험 모드를 추가해 면접관이 다음 흐름을 실제 화면으로 경험하게 한다.

`관리자 화면 → 청첩장 생성 → 고객 역할 전환 → 고객 정보 입력·관리 → 공개 화면 미리보기`

체험 데이터는 모든 방문자가 당일 하나의 작업 공간을 공유하지만 실제 운영 데이터·계정·파일과는 완전히 격리한다.

## 2. 확정된 요구사항

- 메인 화면에 `직접 체험하기` 진입 버튼을 추가한다.
- 실제 관리자·청첩장 위저드·고객 관리·공개 미리보기 UI를 재사용한다.
- 체험 중인 모든 화면 상단에 체험 상태와 종료 동작을 표시한다.
- 실제 Firebase 로그인 없이 체험 관리자와 체험 고객 역할을 전환한다.
- 모든 체험자는 한국시간 기준 같은 날짜의 데이터를 공유한다.
- 기본 데이터는 청첩장 유형 15개로 구성한다.
- 사용자가 생성·편집하는 작업물은 `금일 체험 청첩장` 배지로 구분한다.
- 체험 데이터는 매일 한국시간 00:00에 초기화한다.
- 체험 데이터는 운영 Firestore, 실제 고객 계정, 운영 Storage와 섞이지 않는다.
- 실제 이메일, 결제, 외부 공유처럼 외부 영향을 만드는 기능은 실행하지 않는다.
- 요청하지 않은 운영 배포, Firebase 설정 변경, 커밋은 구현 과정에서도 별도 승인 없이 수행하지 않는다.

## 3. 목표와 비목표

### 목표

1. 로그인 자격증명 없이 핵심 제품 흐름을 1분 안에 시작한다.
2. 체험 화면을 별도 복제품으로 만들지 않고 실제 UI 개선이 체험에도 반영되게 한다.
3. 체험 데이터가 운영 데이터에 기록될 가능성을 구조적으로 차단한다.
4. 여러 방문자가 같은 데이터를 수정하더라도 변경 충돌을 조용히 덮어쓰지 않는다.
5. 자정 이후 이전 날짜의 데이터가 사용자 화면에 다시 나타나지 않게 한다.
6. 익명 사용자가 이용해도 외부 서비스 호출, 악성 파일 업로드, 과도한 비용 발생을 제한한다.

### 비목표

- Firebase 관리자 또는 고객 인증 자체를 체험시키지 않는다.
- 실제 고객 연결 초대 링크와 이메일 인증 과정을 실행하지 않는다.
- 실제 결제, 제작권 지급, 모바일 앱 연동을 체험 범위에 포함하지 않는다.
- 돌잔치, 생일, 일반 행사, 개업 이벤트의 체험 데이터를 만들지 않는다.
- 체험용 UI를 실제 UI와 별도로 복제하거나 독립 디자인 시스템으로 만들지 않는다.
- 임의 이미지 파일을 공용 체험 Storage에 업로드하게 하지 않는다.

## 4. 사용자와 성공 기준

### 주 사용자

프로젝트의 화면 완성도뿐 아니라 관리자와 고객 사이의 실제 업무 흐름, 데이터 연결, 운영 기능을 짧은 시간에 확인하려는 면접관 또는 포트폴리오 방문자다.

### 성공 기준

- 메인 화면에서 체험 시작 버튼을 쉽게 찾을 수 있다.
- 체험 시작 후 로그인 폼 없이 관리자 이벤트 목록이 열린다.
- 초기 관리자 목록에 청첩장 더미 데이터가 정확히 15개 나타난다.
- 새 청첩장 생성 결과가 `금일 체험 청첩장`으로 명확히 구분된다.
- 고객 역할로 전환한 뒤 같은 청첩장의 내용을 편집할 수 있다.
- 고객 저장 결과가 관리자 화면과 공개 미리보기에 반영된다.
- 체험 종료 후 운영 로그인 상태나 운영 데이터에 변화가 없다.
- 날짜가 바뀌면 열린 화면을 포함해 새 날짜 작업 공간으로 이동한다.

## 5. 사용자 여정

### 5.1 체험 시작

메인 히어로의 주요 행동 영역에 `직접 체험하기` 버튼을 추가한다. 버튼을 누르면 다음 내용을 짧게 안내한다.

- 체험 데이터는 오늘의 다른 체험자와 공유된다.
- 실제 개인정보를 입력하지 않는다.
- 데이터는 한국시간 00:00에 초기화된다.

사용자가 동의하면 체험 세션을 발급하고 `/experience/admin`으로 이동한다.

### 5.2 관리자 체험

관리자 화면은 기존 `/admin` UI와 같은 컴포넌트를 사용한다. 체험용 청첩장 15개로 검색, 필터, 상태 조회, 상세 패널, 미리보기를 사용할 수 있다.

기본 더미 15개는 체험 환경의 안정성을 위해 조회 중심으로 제공한다. 수정·삭제·공개 상태 변경의 주 대상은 별도의 당일 작업물이다.

`새 청첩장 만들기`는 `/experience/page-wizard`로 이동한다. 모든 방문자는 생성 위저드를 처음부터 진행할 수 있으며 최종 저장 시 날짜별 단일 당일 작업물을 생성하거나 갱신한다. 중복 작업물을 계속 추가하지 않는다.

당일 작업물은 다음처럼 표시한다.

- 기본 표시명: 사용자가 입력한 신랑·신부 또는 청첩장 이름
- 고정 배지: `금일 체험 청첩장`
- 초기 연결 상태: `체험 고객 연결 대기`

### 5.3 고객 역할 전환

관리자 생성 완료 화면에 `고객 화면으로 전환해 계속 입력하기`를 제공한다. 실제 초대 링크 발급이나 Firebase 로그인 없이 체험 세션의 역할만 `customer`로 변경한다.

역할 변경 후 `/experience/page-wizard/{slug}`로 이동한다. 이 화면은 기존 고객 편집 경계와 동일한 입력·검증·미리보기 경험을 제공하되 체험 API만 사용한다.

### 5.4 고객 관리

`/experience/my-invitations`에는 당일 작업물만 표시한다. 고객은 다음 작업을 체험할 수 있다.

- 청첩장 정보 입력과 수정
- 저장과 공개 상태 확인
- 실제 테마 렌더러 기반 미리보기
- 방명록 조회와 체험 데이터 범위 내 관리
- 관리자 역할로 다시 전환

### 5.5 체험 종료

상단 바의 `체험 종료`는 현재 브라우저의 체험 세션 쿠키와 체험용 클라이언트 캐시만 제거하고 메인으로 이동한다. 공용 당일 데이터는 다른 체험자에게 영향을 주지 않도록 삭제하지 않는다.

## 6. 정보 구조와 라우트

체험 라우트는 `/experience` 아래에 명시적으로 격리한다.

```text
/experience/admin
/experience/page-wizard
/experience/page-wizard/{slug}
/experience/page-wizard/{slug}/result
/experience/my-invitations
/experience/preview/{slug}
```

체험 API도 운영 API와 분리한다.

```text
/api/experience/session
/api/experience/bootstrap
/api/experience/events
/api/experience/events/{slug}
/api/experience/events/{slug}/comments
/api/experience/events/{slug}/images
```

정확한 하위 API 수는 구현 시 기존 화면에서 실제로 호출하는 기능만 포함한다. 체험 UI는 URL 생성 helper를 통해 항상 `/experience/**`로 이동하며 운영 `/admin`, `/page-wizard`, `/my-invitations` 또는 공개 `/{slug}`로 빠지지 않는다.

## 7. UI 구성

### 7.1 체험 상단 바

모든 체험 화면 상단에 다음 항목을 고정 표시한다.

- 상태: `체험 중`
- 현재 역할: `관리자` 또는 `고객`
- `관리자로 전환` 또는 `고객으로 전환`
- `체험 종료`
- `매일 00:00 초기화`
- `실제 개인정보를 입력하지 마세요`

상단 바는 기존 관리자·위저드·고객 화면의 고정 요소와 겹치지 않도록 공통 레이아웃에서 높이를 제공한다. 모바일에서는 핵심 상태와 종료 버튼을 우선 보이고 나머지 안내는 접을 수 있게 한다.

### 7.2 실제 컴포넌트 재사용

기존 화면을 복사하지 않고 실행 모드에 따라 인증과 데이터 공급자만 선택한다.

```text
운영 모드 → AdminProvider + 운영 서비스 + 운영 Repository
체험 모드 → ExperienceProvider + 체험 서비스 + 체험 Repository
```

주요 경계는 다음과 같다.

- `ExperienceProvider`: 체험 활성 상태, 역할, 날짜 만료, 종료 처리
- `ExperienceBanner`: 상단 상태 표시와 역할 전환
- `experienceRoutes`: 체험 내부 링크 생성
- `demoExperienceService`: 클라이언트 체험 API 호출
- `demoExperienceRepository`: 체험 Firestore 경로 접근
- `demoExperienceSeeds`: 날짜 기준 더미 데이터 생성
- `demoExperienceCleanup`: 이전 날짜 문서와 파일 정리

`AdminPageClient`, `PageWizardClient`, `MyInvitationsClient`, 공개 테마 렌더러는 가능한 그대로 재사용한다. 데이터 조회·저장, 인증 판정, 링크 생성처럼 모드에 따라 달라지는 부분만 명시적 인터페이스로 주입한다.

## 8. 데이터 모델과 격리

### 8.1 Firestore 경로

체험 데이터의 source of truth는 운영 `events/{eventId}`가 아니라 아래 전용 경로다.

```text
demoExperiences/{dateKey}
  events/{eventId}
    content/current
    comments/{commentId}
  slugIndex/{slug}
```

`dateKey`는 `YYYY-MM-DD` 형식이며 서버가 `Asia/Seoul` 기준으로 계산한다. 클라이언트가 보낸 날짜나 경로는 신뢰하지 않는다.

체험 Repository는 운영 `eventRepository`를 호출하지 않는다. 반대로 운영 서비스도 `demoExperiences`를 참조하지 않는다. 아키텍처 검증에서 이 import 경계를 확인한다.

### 8.2 Storage 경로

체험에서 사용하는 파일이 필요한 경우 운영 `wedding-images`와 분리된 아래 경로만 사용한다.

```text
demo-wedding-images/{dateKey}/{slug}/...
```

초기 범위에서는 임의 파일 업로드 대신 사전에 준비한 체험 이미지 선택을 제공한다. 이를 통해 부적절한 공용 이미지 노출, 악성 파일, 익명 업로드 비용을 차단한다.

### 8.3 당일 단일 작업물

날짜별로 `kind: daily-workspace`인 이벤트는 최대 하나만 존재한다. 생성 완료 시 트랜잭션으로 해당 작업물을 생성하거나 갱신한다. 화면의 사용자 입력 표시명과 별개로 `금일 체험 청첩장` 배지를 결정하는 시스템 필드를 둔다.

기본 더미 이벤트에는 `kind: seed`를 사용한다. 체험 고객 화면은 `daily-workspace`만 조회하고 관리자 화면은 `seed` 15개와 존재하는 `daily-workspace`를 함께 조회한다.

## 9. 더미 데이터

매일 생성하는 기본 데이터는 모두 `wedding` 이벤트다. 실제 인물이나 업체와 혼동되지 않는 가상 이름과 정보를 사용한다.

15개 데이터는 다음 상태를 고르게 포함한다.

- 공개와 비공개
- 고객 연결과 미연결
- 예식 전, 임박, 종료 상태
- 지원 중인 여러 청첩장 테마
- 서로 다른 최근 수정 시각
- 방명록 있음과 없음

예식일과 수정 시각은 현재 `dateKey`를 기준으로 상대 계산한다. 따라서 고정된 과거 날짜 때문에 오래된 데모처럼 보이지 않는다. seed generator는 동일한 날짜에 항상 같은 결과를 만들어 테스트와 재생성이 가능해야 한다.

## 10. 자정 초기화와 정리

### 10.1 사용자에게 보이는 초기화

모든 체험 API는 요청 시 서버의 현재 `dateKey`를 사용한다. 한국시간 00:00이 지나면 이전 날짜 공간은 즉시 조회 대상에서 제외된다.

브라우저는 다음 한국시간 00:00까지 타이머를 설정한다. 날짜가 바뀌면 React Query 체험 캐시를 제거하고 다음 메시지를 표시한 뒤 새 관리자 화면으로 이동한다.

`새로운 체험일이 시작되어 데이터가 초기화되었습니다.`

서버가 먼저 날짜 변경을 감지한 경우 `DEMO_DAY_ROLLED_OVER` 코드로 응답하고 클라이언트는 같은 전환 절차를 수행한다.

### 10.2 새 날짜 초기 데이터

새 날짜의 첫 bootstrap 요청이 seed 생성을 수행한다. 여러 요청이 동시에 들어와도 lease 또는 Firestore 트랜잭션을 사용해 15개가 한 번만 생성되게 한다.

### 10.3 물리적 정리

자정 정리 작업은 이전 날짜의 체험 문서와 `demo-wedding-images` 파일만 대상으로 한다. 정리 작업이 실패하거나 지연되어도 당일 API는 현재 `dateKey`만 조회하므로 전날 데이터가 사용자에게 노출되지 않는다.

자동 정리 인프라가 필요한 배포 작업은 구현과 검증 후 별도 승인을 받아 적용한다. 배포 전에는 로컬 또는 Firebase Emulator에서 정리 대상을 검증하고 운영 컬렉션과 Storage prefix가 포함되지 않는지 확인한다.

## 11. 동시 수정

모든 방문자가 하나의 당일 작업물을 공유하므로 이벤트 본문에 단조 증가하는 `version`을 둔다.

1. 편집 조회 응답이 현재 `version`을 반환한다.
2. 저장 요청이 사용자가 편집을 시작한 버전을 함께 전송한다.
3. 서버 트랜잭션이 저장 직전 버전을 비교한다.
4. 버전이 같으면 저장하고 `version + 1`을 기록한다.
5. 버전이 다르면 `409 VERSION_CONFLICT`로 응답한다.

충돌 시 화면은 다음 안내와 동작을 제공한다.

- 안내: `다른 체험자가 먼저 수정했습니다. 최신 내용을 불러온 뒤 다시 저장해 주세요.`
- 기본 동작: 현재 입력을 조용히 덮어쓰지 않음
- 선택 동작: 최신 내용 불러오기

초기 구현에서는 전체 설정 단위 낙관적 잠금을 사용한다. 자동 병합이나 실시간 공동 편집은 범위에 포함하지 않는다.

## 12. 역할과 세션

체험 시작 시 서버가 서명된 세션 쿠키를 발급한다.

- `HttpOnly`
- `Secure` (운영 환경)
- `SameSite=Lax`
- 만료: 다음 한국시간 00:00
- 포함 정보: 체험 세션 식별자, 현재 역할, 발급 날짜

체험 역할은 `admin`과 `customer` 두 가지다. 이 역할은 체험 API 안에서만 유효하며 운영 관리자 권한이나 실제 이벤트 소유권으로 해석하지 않는다.

역할 전환은 서버가 세션을 갱신한 뒤 해당 체험 라우트로 이동한다. 브라우저에서 임의로 역할 문자열을 바꾸는 것만으로 권한이 변경되지 않도록 API가 서명된 세션을 검증한다.

## 13. 안전과 보안

### 금지 또는 대체할 동작

- 실제 고객 연결 링크 발급과 이메일 전송
- Firebase 회원가입과 실제 계정 생성
- 결제, 제작권, 지갑 잔액 변경
- 카카오 공유 등 외부 공유
- 운영 이벤트, 고객, 방명록, 이미지 삭제
- 익명 사용자의 임의 이미지 파일 업로드

금지된 동작은 숨겨 화면 구조를 크게 바꾸기보다, 체험용 대체 동작 또는 명확한 비활성 안내를 제공한다. 고객 연결은 체험 역할 전환으로 대체하고 이미지는 승인된 샘플 선택으로 대체한다.

### API 보호

- 서명된 체험 세션 검증
- 서버 계산 `dateKey` 강제
- 요청 Origin 확인
- 세션 식별자와 IP를 조합한 rate limit
- 기존 입력 정규화, HTML escaping, 이미지 정책 재사용
- 텍스트 필드 길이 제한
- Firestore Rules에서 체험 경로의 클라이언트 직접 접근 차단
- 체험 저장 경로와 운영 저장 경로의 import 경계 검사

공용 데이터라는 특성상 모든 체험 안내에서 실제 개인정보를 입력하지 말라고 명시한다.

## 14. 오류와 상태 처리

### 초기 데이터 생성 실패

관리자 화면을 빈 목록으로 표시하지 않고 `체험 데이터를 준비하지 못했습니다`와 다시 시도를 제공한다.

### 날짜 변경

열린 폼을 더 이상 저장하지 않고 새 날짜 초기화 안내 후 체험 관리자 화면으로 이동한다.

### 버전 충돌

입력 내용을 조용히 덮어쓰거나 자동 저장하지 않는다. 최신 내용 불러오기 전에는 재저장을 막는다.

### 세션 만료 또는 위조

체험 시작 안내 화면으로 이동하고 운영 로그인으로 대체하지 않는다.

### 금지된 외부 동작

`체험 모드에서는 실제 발송·결제·외부 공유를 실행하지 않습니다.`라고 안내한다.

### 정리 실패

현재 날짜 조회에는 영향을 주지 않는다. 서버 로그에 정확한 체험 날짜와 단계만 남기며 입력 본문이나 세션 쿠키는 기록하지 않는다.

## 16. 검증 계획

### 단위 검증

- 한국시간 `dateKey`와 다음 자정 계산
- seed generator가 정확히 15개의 wedding 이벤트 생성

- 버전 일치 저장과 충돌 판정

- 체험 API가 `demoExperiences/{dateKey}`만 읽고 씀
- 클라이언트가 임의 날짜를 전달해도 현재 날짜만 사용

- 새 청첩장 생성과 배지 확인

- 관리자·고객·위저드·미리보기의 상단 체험 바 확인

## 18. 결정 사항

- Firestore 체험 전용 namespace 방식을 사용한다.
- 운영 `events`에 `isDemo` 같은 구분 필드를 추가하지 않는다.
- 브라우저 localStorage만으로 체험 데이터를 저장하지 않는다.
- 모든 방문자는 날짜별 공용 데이터를 공유한다.
- 기본 데이터는 청첩장 15개로 한정한다.
- 고객 연결은 실제 인증이 아니라 서명된 체험 세션의 역할 전환으로 표현한다.
- 기존 UI 컴포넌트를 재사용하고 데이터 접근과 링크만 모드별로 분리한다.
- 기본 15개는 안정적인 조회 데이터로 유지하고 당일 작업물만 자유롭게 수정한다.
- 동시 수정은 전체 설정 단위 낙관적 잠금과 409 충돌 안내로 보호한다.
- 자정에는 서버 날짜 namespace 전환으로 사용자에게 즉시 초기화된 상태를 보장한다.
- 임의 이미지 업로드와 실제 외부 발송·결제·공유는 체험 범위에서 실행하지 않는다.
