# 웹 서비스 안정성 강화 설계

## 1. 목적

웹과 공통 서버 영역의 현재 동작을 보존하면서 인증·권한, API·Repository 경계,
Firebase Rules, 회귀 테스트, 운영 문서의 불일치를 위험도 순서로 점검하고
확인된 문제만 최소 수정한다.

이번 안정화는 특정 장애 대응이 아니라 현재 코드 기준의 예방적 감사와 회귀 방지
기반 구축을 목적으로 한다.

## 2. 적용 범위

### 포함

- Next.js 웹 애플리케이션
- Next.js API Routes
- `src/server` 서버 서비스와 Repository
- `src/services`의 클라이언트 서비스와 Repository 경계
- Firestore Rules와 Storage Rules
- Firebase Emulator 기반 권한 테스트
- 웹과 공통 서버의 회귀 테스트
- Expo 모바일 앱이 사용하는 API 계약의 영향 검증
- 현재 운영 구조를 설명하는 핵심 문서

### 제외

- Expo 모바일 UI와 네이티브 기능의 전면 수정
- Firestore 저장 스키마 변경과 데이터 마이그레이션
- 공개 URL 변경
- 기존 API 요청·응답 계약 변경
- 운영 Firebase 데이터 생성·수정·삭제
- Firebase Rules 또는 웹 애플리케이션 배포
- 운영 환경 변수와 Secret Manager 변경
- 새 외부 의존성 추가
- 사용 여부가 입증되지 않은 API의 즉시 삭제

제외 범위의 변경이 필요해지면 현재 작업을 멈추고 별도 승인을 받는다.

## 3. 핵심 원칙

1. 문서보다 실제 코드, 라우트, 스크립트, Rules를 최종 기준으로 삼는다.
2. 각 영역은 `현황 확인 → 실패 테스트 → 최소 수정 → 관련 검증` 순서로 처리한다.
3. 문제가 확인되지 않은 코드는 정리 목적만으로 수정하지 않는다.
4. 공개 URL, API 계약, 저장 스키마, 현재 UX를 보존한다.
5. 보안 문제는 테스트로 재현한 뒤 최소 범위로 수정한다.
6. Rules를 테스트 통과 편의를 위해 완화하지 않는다.
7. 모바일 앱은 공통 API 계약 영향만 확인하고 UI 수정 범위로 확장하지 않는다.
8. 각 작업 묶음은 독립적으로 검토하고 검증할 수 있어야 한다.

## 4. 단계별 안정화 구조

### 4.1 기준선 확정

- 현재 `package.json`에 정의된 검증 명령을 실행한다.
- 실패가 있으면 기존 실패와 환경 의존 실패를 구분해 기록한다.
- `src/app`의 실제 페이지 및 API 라우트 목록을 만든다.
- 인증 주체, 호출 서비스, Repository, Firestore/Storage 리소스의 대응표를 만든다.
- 이 단계에서는 런타임 동작을 변경하지 않는다.

### 4.2 인증·권한 안정화

- 관리자, 고객, 공개 방문자, 모바일 편집 세션, 모바일 고위험 재인증의 경계를
  각각 확인한다.
- 토큰 없음, 만료·위조 토큰, 비활성 관리자, 타인 이벤트 접근, 잘못된 slug
  세션을 회귀 테스트로 고정한다.
- 여러 고객 API에 중복된 Bearer 토큰 해석과 Firebase ID 토큰 검증은
  `src/server/customerApiAuth.ts` 계열을 기준으로 통합한다.
- 관리자 API는 `src/server/adminApiAuth.ts`의 활성 관리자 검증을 기준으로 한다.
- 모바일 편집 API는 서버 발급 세션의 slug와 권한 목록을 모두 확인한다.
- 링크 토큰 등 고위험 작업은 기존 추가 재인증 단계를 유지한다.

### 4.3 API·Repository·오류 처리 안정화

정상 호출 경계는 다음과 같다.

```text
웹/모바일 클라이언트
→ API Route
→ 인증·입력 검증·레이트리밋
→ Server Service
→ Server Repository
→ Firestore / Storage
```

- API Route는 HTTP 요청 해석과 응답 생성을 담당한다.
- Server Service는 생성, 편집, 결제, 소유권 같은 업무 흐름을 조합한다.
- Firestore 컬렉션 경로와 쿼리는 `src/server/repositories/**`가 담당한다.
- `src/services`의 Firestore 직접 접근은 `src/services/repositories/**`로 제한한다.
- 고객이 제출한 `ownerUid`, 상품 등급, 기능 플래그, 티켓 관련 값을 권한 판단의
  근거로 사용하지 않는다.
- 고객 제작권 차감과 이벤트 생성처럼 여러 쓰기가 연결된 흐름은 실패 시 보상
  동작과 중복 실행 안전성을 검증한다.
- 결제 이행은 `transactionId` 기준 멱등성을 유지한다.
- 운영 환경의 민감 API는 레이트리밋 저장소 실패 시 허용되지 않아야 한다.
- 예상하지 못한 서버 예외는 내부 로그에 남기고 API 응답에는 안전한 공통 문구만
  노출한다.

### 4.4 Firebase Rules 일치성

서버 정책과 Firestore/Storage Rules는 다음 경우에 같은 결론을 내려야 한다.

- 공개 이벤트는 공개 상태이며 유효한 노출 기간 안에 있을 때만 익명 조회 가능
- 비공개, 노출 전, 노출 종료 이벤트는 익명 조회 차단
- 소유자는 본인 이벤트만 허용된 범위에서 관리 가능
- 관리자는 활성 `admin-users` 문서가 있을 때만 관리 가능
- 상품 등급, 기능 플래그, 티켓, 소유권, slug 연결 정보는 고객 직접 변경 차단
- 공개 방명록 작성은 서버 API를 통하고 Firestore 클라이언트 직접 생성은 차단
- Storage 공개 다운로드는 이벤트 공개 상태와 노출 기간을 동일하게 적용
- Storage 목록, 업로드, 삭제는 관리자 또는 해당 이벤트 소유자만 허용
- 이미지 업로드는 허용 용량과 이미지 MIME 조건을 충족해야 함

정책 불일치가 발견되면 서버, 클라이언트, Rules 중 의도된 정책을 벗어난 위치를
확인한 후 최소 수정한다.

### 4.5 회귀 테스트 보강

- 기존 정적 경계 검사는 유지한다.
- 인증 Helper와 대표 API Route는 함수 단위 동작 테스트를 추가한다.
- Firestore Emulator 테스트는 공개 기간, 보호 필드, 서버 전용 컬렉션,
  slug index, 방명록 권한 시나리오를 포함한다.
- Storage Rules는 별도 Emulator 회귀 테스트를 추가한다.
- 모바일 API의 URL, 요청 필드, 응답 타입을 변경하지 않고 모바일 lint와
  typecheck로 영향을 확인한다.

### 4.6 문서 동기화

다음 문서를 실제 코드와 라우트 기준으로 갱신한다.

- `README.md`
- `docs/security-hardening-checklist.md`
- `docs/service-repository-boundary.md`
- `docs/event-type-registry.md`
- `docs/portfolio-service-overview.md`
- `docs/ai-harness-handoff.md`

특히 현재 `src/app`에 없는 `/page-editor` 설명, 실제 경로와 다른 개업 위저드
설명, 이벤트 타입 레지스트리의 누락을 정리한다. 인수인계 문서는 현재 운영
기준과 과거 작업 이력을 구분한다.

## 5. 인증·권한 모델

| 주체 | 인증 기준 | 허용 범위 |
| --- | --- | --- |
| 공개 방문자 | 인증 없음 | 공개 조건을 통과한 초대장·이미지 조회와 제한된 방명록 작성 |
| 고객 | Firebase ID 토큰 | `ownerUid`가 일치하는 이벤트 조회, 허용된 편집, 방명록 관리 |
| 관리자 | Firebase ID 토큰과 활성 `admin-users` 문서 | 관리자 API와 전체 운영 기능 |
| 모바일 편집자 | 서버 발급 편집 세션과 권한 목록 | 세션에 명시된 기능 |
| 모바일 고위험 작업 | 편집 세션과 추가 재인증 토큰 | 링크 토큰 및 민감 설정 작업 |

### HTTP 오류 기준

- 입력 형식 또는 필수값 오류: `400`
- 인증 정보 없음, 만료, 위조: `401`
- 인증은 유효하지만 권한 부족: `403`
- 서버 인증 구성 초기화 실패: `500`
- 예기치 않은 서버 오류: 기존 상태 코드를 보존하면서 안전한 공통 메시지 반환

기존 API의 세부 상태 코드와 응답 필드가 위 기준과 다를 경우 바로 변경하지 않고
호환성 테스트를 먼저 추가한다.

## 6. 호환성 보존

- `/{slug}`와 `/{slug}/{theme}` 공개 경로를 유지한다.
- 관리자, 고객, 모바일 API의 URL과 요청·응답 필드를 유지한다.
- `events/{eventId}`, `events/{eventId}/content/current`,
  `eventSlugIndex/{slug}` 중심 저장 구조를 유지한다.
- 현재 UI가 없는 `/api/client-editor/**`는 사용처와 호환성을 먼저 조사한다.
- 사용되지 않는 것이 입증되더라도 제거는 별도 승인과 별도 계획으로 처리한다.
- 권한 강화로 기존 정상 사용자가 차단될 가능성이 있으면 변경 전에 시나리오와
  영향 범위를 보고한다.

## 7. 검증 전략

### 단계별 검증 순서

1. 수정 대상의 실패 테스트
2. 해당 인증, API, Repository 또는 Rules 테스트
3. `npm run lint:web`
4. `npm run typecheck:web`
5. 기존 보안·Repository 경계·회귀 테스트
6. Firestore 및 Storage Emulator 테스트
7. `npm run lint:mobile`
8. `npm run typecheck:mobile`
9. `npm run build`

### 필수 인증·API 시나리오

- 토큰 없음
- 만료 또는 위조된 토큰
- 비활성 관리자
- 일반 고객의 관리자 API 접근
- 소유자의 본인 이벤트 접근
- 다른 고객 이벤트 접근
- 요청 본문의 `ownerUid` 조작
- 상품 등급, 기능 플래그, 티켓 관련 필드 조작
- 만료되거나 다른 slug에 발급된 모바일 세션
- 고위험 재인증 없는 민감 작업
- 결제 이행 중복 요청
- 제작권 차감 후 이벤트 생성 실패

### 필수 Rules 시나리오

- 공개 이벤트와 비공개 이벤트
- 노출 시작 전과 종료 후
- 기간 비활성 상태와 잘못된 기간 데이터
- 소유자와 다른 고객
- 활성 관리자와 비활성 관리자
- 이벤트 본문 보호 필드 변경
- slug index의 slug 또는 eventId 변경
- 공개 방문자의 방명록 직접 생성
- 서버 전용 컬렉션의 클라이언트 접근
- Storage 공개 다운로드, 목록, 업로드, 삭제
- 이미지가 아닌 파일과 허용 용량 초과 파일

## 8. 작업 분해

안정화는 다음 네 묶음으로 분리한다.

1. 인증·권한 안정화
2. API·Repository·오류 처리 안정화
3. Firestore·Storage Rules 및 Emulator 테스트
4. 전체 회귀 검증과 문서 동기화

각 묶음은 이전 단계의 공개 인터페이스를 소비하며 독립적으로 검토 가능한 테스트
결과를 만들어야 한다. 한 묶음의 변경이 다음 묶음의 전제와 충돌하면 구현을
계속하지 않고 설계를 다시 확인한다.

## 9. 중단 및 승인 조건

다음 상황에서는 임의로 진행하지 않는다.

- 저장 스키마 또는 데이터 마이그레이션이 필요함
- 공개 URL 또는 API 계약 변경이 필요함
- 기존 Firebase Rules 권한을 넓혀야 함
- 새 외부 의존성이 필요함
- 운영 데이터, 운영 환경 변수, Secret Manager 변경이 필요함
- 배포가 필요함
- 기존 실패와 이번 변경의 실패를 구분할 수 없음
- 정상 사용자의 기존 권한을 축소할 가능성이 있음

## 10. 완료 기준

- 기존 공개 URL, API 계약, Firestore 저장 구조가 유지된다.
- 인증 주체별 허용·차단 시나리오가 테스트로 고정된다.
- API와 서버 서비스에 Repository 경계를 우회하는 Firestore 접근이 없다.
- 서버 공개 정책과 Firestore·Storage Rules 결과가 일치한다.
- 관련 테스트와 웹 lint, typecheck, build가 통과한다.
- 모바일 lint와 typecheck로 공통 API 계약 영향을 확인한다.
- 실제 라우트와 핵심 운영 문서가 일치한다.
- 공개 화면, 고객 화면, 관리자 접근 차단을 가능한 범위에서 브라우저로 확인한다.
- 실행하지 못한 운영 환경 검증과 남은 위험을 완료 보고에 명시한다.

## 11. 산출물

- 단계별 감사 결과와 확인된 문제 목록
- 실패를 재현하는 회귀 테스트
- 테스트를 통과시키는 최소 코드 또는 Rules 수정
- 최신 코드와 일치하는 핵심 운영 문서
- 실행한 검증 명령과 결과
- 운영 환경에서만 확인 가능한 남은 위험

커밋, 푸시, 배포는 사용자가 별도로 요청하기 전까지 수행하지 않는다.
