# 고객 URL 기반 편집 권한 설계

## 목표

관리자만 초대장 페이지를 생성하고, 생성된 편집 URL을 전달받은 로그인 고객은 최초 한 번 명시적으로 편집을 시작하여 자신의 계정에 페이지를 연결한 뒤 기존 편집 기능을 그대로 사용한다.

## 권한 규칙

- 페이지 생성은 기존과 같이 관리자만 가능하다.
- 새로 생성된 페이지의 `ownerUid`는 비워 둔다.
- 소유자가 없는 페이지는 로그인한 일반 고객에게 `claimable`로 노출한다.
- 과거 생성 과정에서 관리자 계정이 소유자로 기록된 페이지도 `claimable`로 취급한다.
- 고객은 `이 계정으로 편집 시작`을 눌러야 소유권을 가져간다. URL 열람만으로는 연결하지 않는다.
- 소유권 확정은 Firestore 트랜잭션으로 처리한다. 소유자가 없거나 활성 관리자일 때만 고객 UID로 변경하며, 이미 다른 고객이 소유한 경우 거절한다.
- 관리자 계정은 고객용 선점 API로 페이지를 가져갈 수 없다.
- 선점 후 자동 저장, 이미지 업로드, 최종 저장은 기존 소유 고객 흐름을 사용한다.
- 최종 저장을 마치면 해당 페이지는 고객 관리 화면의 보유 페이지 목록에 나타난다.

## 화면 흐름

1. 고객이 `/page-wizard/{slug}`에 로그인하여 접근한다.
2. 미연결 또는 기존 관리자 소유 페이지이면 안내 화면과 `이 계정으로 편집 시작` 버튼을 표시한다.
3. 버튼을 누르면 서버가 원자적으로 소유권을 확정한다.
4. 성공하면 편집 데이터를 다시 불러와 실제 편집 화면으로 진입한다.
5. 다른 고객이 먼저 가져간 경우 현재 계정으로 편집할 수 없다는 안내를 표시한다.

## 오류 처리

- 존재하지 않는 URL: 페이지를 찾을 수 없다는 기존 안내를 유지한다.
- 인증되지 않은 요청: 401을 반환한다.
- 관리자 계정의 고객 선점 요청: 403을 반환한다.
- 다른 고객 소유 페이지: 409를 반환하고 기존 소유권을 보존한다.
- 동시 선점: 트랜잭션에서 한 요청만 성공하고 나머지는 409로 종료한다.

## 검증

- 소유자 없음, 관리자 소유, 동일 고객 소유, 다른 고객 소유에 대한 정책 테스트
- 고객 선점 API와 편집 화면 연결 계약 테스트
- 기존 관리자 생성 시 미연결 유지 테스트
- 타입 검사, 린트, 빌드
